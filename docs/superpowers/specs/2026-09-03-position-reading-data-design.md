# 위치별 타로 해석 데이터 설계

## 목표

런타임 AI 호출 없이 카드, 방향, 주제, 배열법, 위치에 맞는 구체적인 해석을 Supabase에서 바로 제공한다. 사용자 신분이나 상황을 추가로 묻지 않으며, 특히 `일·커리어`는 업무·평가·과제·시험·지원·면접처럼 현실에서 바로 이해할 수 있는 표현을 사용한다.

## 저장 단위

새 테이블 `tarot_position_readings`의 한 행은 다음 조합 하나를 나타낸다.

- 카드: 78장
- 방향: `upright`, `reversed`
- 주제: 기존 8개
- 방식: `one`, `three`, `celtic`, `horoscope`
- 배열: 원 오라클 1개, 쓰리카드 5개, 켈틱 크로스 1개, 호로스코프 1개
- 위치: 원 오라클 1개, 쓰리카드 15개, 켈틱 크로스 10개, 호로스코프 12개

총 위치 수는 38개이며 전체 행 수는 `78 × 2 × 8 × 38 = 47,424`개다.

각 행은 식별자 외에 `headline`, `summary`, `detail`, `advice`, `reflection_question`만 가진다. 카드 이름, 이미지, 키워드와 기본 해석은 기존 테이블을 참조해 중복 저장하지 않는다.

## 문장 생성 원칙

데이터는 배포 전 SQL 마이그레이션에서 기존 카드별 기본 해석을 바탕으로 생성하고 영구 저장한다. 서비스 요청 중에는 AI나 문장 생성 API를 호출하지 않는다.

- 과거: 이미 지나갔지만 현재에 영향을 남긴 사건을 과거형으로 쓴다.
- 현재: 지금 드러나는 상황과 당장 확인할 행동을 현재형으로 쓴다.
- 미래: 현재 흐름이 이어질 때 가능한 결과를 미래형·가능성 표현으로 쓴다.
- NO: 피하거나 중단해야 할 조건을 분명하게 쓴다.
- 보류: 결정을 미루고 확인해야 할 정보나 신호를 쓴다.
- YES: 진행해도 좋은 구체적인 조건을 쓴다.
- 켈틱 크로스와 호로스코프: 각 위치의 질문 역할에 맞춰 동일한 카드도 다른 문장으로 저장한다.
- 일·커리어: 추상 키워드를 그대로 노출하지 않고 평가, 역할, 협업, 과제, 시험, 지원, 면접 등 실제 장면으로 번역한다.

## 조회와 결과 조합

원 오라클, 쓰리카드, 켈틱 크로스 API는 선택된 카드의 위치별 행만 조회한다. 결과 조합 코드는 저장된 문장을 순서대로 연결하고, 쓰리카드 결론은 배열별 규칙으로 만든다. 특정 위치 데이터가 없을 때만 기존 `tarot_topic_readings`를 임시 폴백으로 사용한다.

호로스코프 화면은 이번 작업에서 만들지 않는다. 대신 12하우스 위치 데이터까지 생성하여 이후 화면 구현 시 같은 테이블을 바로 사용할 수 있게 한다.

## 용량과 인덱스

유일 키는 `(card_id, topic_id, orientation, reading_type, layout_id, position_id)`다. API 조회에 필요한 동일한 열 조합의 인덱스 하나만 둔다. 긴 기본 해석과 카드 메타데이터를 반복하지 않아 무료 플랜 500MB 안에서 운영할 수 있도록 한다.

## 적용과 검증

마이그레이션은 여러 번 실행해도 같은 47,424개 조합으로 수렴하도록 upsert 방식으로 작성한다. 검증은 전체 행 수와 방식별 행 수, 필수 문장 공백 여부, 쓰리카드 시간형 및 NO·보류·YES 역할을 확인하는 최소 테스트로 제한한다.
